# Architecture Decision Records (ADRs)

Canonical architectural constraints and invariants governing the Cliffracer runtime.

## ADR-0001: Persistence Boundary
- **Status**: Accepted
- **Context**: Services frequently require database access, but coupling persistence drivers or ORMs to the core messaging framework creates bloat and imposes unwanted opinions.
- **Decision**: Cliffracer does not own persistence. There is no database driver, connection pool, repository abstraction, or migration tool in core. The boundary holds for every distribution in this repository: no first-party extension depends on or imports an external datastore (SQL, document or cache server). State the broker holds, streams and Key-Value, is inside it.
- **Consequences**: Applications manage their own persistence layers and connection pools. Persistence additions to core are out of scope.

## ADR-0002: Core HTTP Endpoint Scope
- **Status**: Accepted
- **Context**: Orchestrators and probes require HTTP health checks, but pulling in full HTTP frameworks (FastAPI, Starlette) into core adds substantial dependency overhead.
- **Decision**: Core provides built-in HTTP serving exclusively for the four probe routes `GET /live`, `GET /ready`, `GET /health` and `GET /info`, using Python stdlib `asyncio`. `/health` is the backward-compatible alias of `/ready`. No other route is served.
- **Consequences**: Services answer container/Kubernetes probes without requiring external web frameworks.

## ADR-0003: Health Endpoint Status Code Semantics
- **Status**: Accepted
- **Context**: Container orchestrators and simple curl healthchecks rely on HTTP status codes to detect service liveness and readiness without parsing response bodies.
- **Decision**: `/health` returns HTTP 200 when healthy and HTTP 503 when unhealthy, when any active dependency probe fails, or when evaluating health itself raises (the body then reads `status: "error"`). `/ready` answers the same way. `/live` runs no dependency probe and does not read the broker's state: it answers 200 while the service is running and 503 once it is stopped, so a failing probe or a disconnected broker degrades `/ready` and `/health` and leaves `/live` at 200. An extension's `health_details()` is informational: it is added to the body and never changes the status or the status code, and an extension that must gate readiness registers a dependency probe. `/info` is no probe, and a failure building it is a 500.
- **Consequences**: Health status is immediately evaluable by `curl -f` and orchestrator probes without requiring JSON payload parsing.

## ADR-0004: Extension Composition Over Class Mixins
- **Status**: Accepted
- **Context**: Class inheritance mixins create complex Method Resolution Order (MRO) interactions, implicit state collisions, and rigid coupling.
- **Decision**: Optional features and capabilities are composed via extensions declared as class attributes and bound per service instance.
- **Consequences**: Extensions do not join the class MRO. Extension lifecycles are explicitly supervised by the container, ensuring clean encapsulation, independent packaging, and clear execution boundaries.

## ADR-0005: Extension Immutability and Instance Isolation
- **Status**: Accepted
- **Context**: Service class attribute definitions are shared across instances. Mutable state on declared attributes would cause state bleed across service instances in the same process.
- **Decision**: Extension attributes declared on service classes act as immutable factory specifications. `bind()` constructs a fresh runtime instance and isolates declaration arguments per service instance.
- **Consequences**: Runtime state is strictly isolated between service instances. Passing uncopyable objects or mutating extension specifications at runtime fails loudly.
- **Copy rule**: An argument is copied implicitly only when it is plain data (lists, dicts, sets, tuples, pydantic models, dataclasses and value types). Any other object that is copied warns with a `FutureWarning` naming the extension and argument, and a later release refuses it unless it is a `SharedDependency` or a zero-argument factory, so that an object which must be one per process is never cloned because it happens to be copyable.
- **Freeze point**: A specification is frozen when a class body declares it, and one passed to `add_extension` when it is bound. Runtime instances are built from the constructor arguments captured at construction, so a write to a specification at any later time would otherwise be discarded without a sign. Freezing copies the declaration arguments, so changing a declared collection in place afterwards cannot reach an instance built later.

## ADR-0006: Explicit Message Refusal Channel
- **Status**: Accepted
- **Context**: Pre-dispatch hook failures need differentiated handling between intentional policy rejections (e.g., authentication failures) and unintentional hook crashes.
- **Decision**: `RejectMessage` raised from `worker_setup` is the hook exception that changes dispatch outcome. The handler is skipped. A terminal refusal is acknowledged, while its `RetryMessage` subtype NAKs durable deliveries after the requested delay. Subclasses are refusals: a host or middleware that classifies exceptions tests with `isinstance`, never the exact type. An extension that declares `fails_closed = True` has any other exception out of its own `worker_setup` converted into a refusal marked as a service fault: the handler is skipped, the caller is told the extension failed rather than that it was refused, and a durable delivery takes the handler-failure path. Every other hook exception is logged and swallowed.
- **Consequences**: Uncaught hook errors do not take down message dispatch, and a gate that crashes does not let the message through. Static policy refusals do not trigger redelivery storms, while temporary capacity decisions preserve durable work. A refused event leaves one WARNING line, `event <subject> refused by an extension (correlation_id: ...): <reason>`, and a count under `rejected` when the metrics extension is declared (`test_a_refusal_is_counted_as_rejected_and_not_as_an_error`); it publishes nothing, so there is no per-message record of a refusal beyond that line (`test_a_refused_jetstream_event_leaves_one_warning_line_and_publishes_nothing`). There is no send-side refusal: `before_call` cannot cancel a send, and a `RejectMessage` raised from it is logged like any other hook exception and the message is sent (`test_a_reject_message_from_before_call_is_logged_and_the_message_is_still_sent`). A send hook may change the message's headers and nothing else. No refusal an extension authored publishes to the DLQ: it receives invalid messages, deliveries that have exhausted their retries, and the deliveries refused by a crashed `fails_closed` hook, which take the handler-failure path.

## ADR-0007: Graceful Service Stop on Terminal Connection Loss
- **Status**: Accepted
- **Context**: When the broker connection is closed for good the service has nothing left to consume, and exiting the process would take every co-located service in that Python process down with it.
- **Decision**: When a broker connection is permanently closed, the service triggers graceful wind-down via `await self.stop()` and does not exit the process. The stop is bounded at 10 seconds, a fixed limit that `shutdown_timeout` does not govern. A stop cut off before the service's `on_shutdown` still runs it, shielded and bounded by `shutdown_timeout`, or by a fixed 30 seconds when that is `None`, so the close callback can take up to that long longer than the cut-off. `ServiceConfig.exit_on_closed=False` keeps the service up, reporting `disconnected`.
- **Consequences**: Co-located services sharing the Python process continue operating normally if unaffected. The process itself stays up, so something has to restart a stopped service: `cliffracer run` polls the connection state every second, stops the service on a close and starts a fresh one while `auto_restart` is true; a service started with `run()` returns from it; an application embedding `start()` watches `is_running` or `/health` itself. The close callback runs inside nats-py's own close, so the stop does not drain a connection that is already closed.

## ADR-0008: Default Infinite Reconnection
- **Status**: Accepted
- **Context**: Ephemeral network partitions or broker restarts should not kill running application processes.
- **Decision**: `max_reconnect_attempts` defaults to `-1` (reconnect indefinitely).
- **Consequences**: Services remain alive during broker outages and resume operation automatically upon broker restoration. Under the default, the connection closes for good in two ways: an explicit administrative disconnect, or an error the server sends that nats-py treats as terminal and does not retry (an authorization violation after a credential change, a connection or subscription limit, an invalid subject). A finite `max_reconnect_attempts` adds a third, its exhaustion; `0` and `-1` both mean no limit in nats-py.
- **What it does not cover**: A partition that drops packets without resetting the socket is noticed through nats-py's ping defaults, `ping_interval` 120 seconds and `max_outstanding_pings` 2 by default, which `ServiceConfig.ping_interval` and `ServiceConfig.max_outstanding_pings` change when set, so with the defaults reconnection can start minutes after the partition: between 240 and 360 seconds. Readiness does not wait for that: `/ready` sends the broker a round trip and reports `disconnected` when it is not answered within `broker_probe_timeout`, 2 seconds by default. Publishes made during the gap buffer in nats-py up to its 2 MiB `pending_size` and then raise; an RPC waits its `request_timeout`. `on_connect` runs again after every reconnection, so it must be safe to run more than once. A JetStream consumer resumes only if the broker kept its durable across the outage, which is the operator's storage choice.

## ADR-0010: Fail-Fast Startup Validation Over Permissive Defaults
- **Status**: Accepted
- **Context**: Ambiguous service configurations or invalid handler signatures can easily cause silent runtime data loss or unrouted messages in production.
- **Decision**: When configuration or type contracts are ambiguous, Cliffracer fails loudly at startup with explicit errors rather than falling back to permissive defaults. Configuration and type refusals are made before the service connects; a refusal that needs broker state, such as a declared stream that conflicts with the one on the broker, is made after the connection, because that is the earliest it can be read. One permissive default is deliberate: a payload that arrives with no content type is read as JSON or msgpack, whichever it is, for senders that set none; a payload that has a content type is read as that type and is not sniffed.
- **Consequences**: Misconfigurations are caught immediately at boot or test time rather than manifesting as silent runtime failures in production.

## ADR-0011: Structured Assertions Over Substring Matching
- **Status**: Accepted
- **Context**: Substring matching in validation, tests, and routing is fragile and prone to false positives caused by coincidental substring occurrences.
- **Decision**: All checks and verifications must parse structured payloads, inspect exact schema fields, or verify process exit codes rather than relying on unanchored substring matching.
- **Consequences**: Eliminates brittle tests and false positives in runtime payload inspection.
- **Permitted signals**: A decision is made on a structured signal: an exception's class, a reply's typed `code`, an `APIError`'s `err_code`, a subject's tokens, a header's key, a process's exit code, or exact equality on a schema field. An RPC error reply carries a `code` (`validation_failed`, `unknown_method`, `refused`, `deadline_exceeded`, `busy`, `internal`), and a caller classifies on it; a streamed reply is item messages, then one such envelope, which carries the `code`; the reply's message text is read only for a reply with no `code`, which a service that has not been redeployed sends. A guard reads `src/` by syntax tree for both halves, and the one function that reads reply text, `raise_for_error_envelope`, is named in it with its reason. Tests are out of scope: `pytest.raises(Typed, match=...)` stays.

## ADR-0012: Bounded Initial Connection Timeout
- **Status**: Accepted
- **Context**: While infinite reconnection is desirable after establishing an initial connection, `nats-py` hangs indefinitely on initial dial when the broker is unreachable and `max_reconnect_attempts` is `-1`.
- **Decision**: `ServiceConfig.connect_timeout` enforces an explicit timeout (default 30s) on initial broker dial, measured in wall-clock time across all of nats-py's retries rather than per attempt. If the broker is unreachable, startup raises `NatsError` once the timeout expires. `connect_timeout=None` opts out: the first dial is governed again by `max_reconnect_attempts`, where `-1` and `0` both mean forever. Reconnects after a connection exists are not affected.
- **Scope**: The bound is on a service's own broker connection. `ServiceClient` takes its own `connect_timeout`, default 30 seconds, with the same wall-clock meaning, and `None` opts out (`test_the_default_bound_matches_the_service_side`). The generator's describe request bounds its whole dial, the one reconnect attempt included, by its own timeout, and the reply by the same timeout again (`test_the_generator_dial_is_bounded_by_its_timeout_and_one_reconnect`, `test_a_dial_that_gets_no_answer_ends_at_the_timeout_and_exits_3`). The metrics connection pool bounds each connection by its own `connect_timeout`, which defaults to `None`, and by `max_reconnect_attempts`, which defaults to 10. A dial the bound cuts off closes the client it opened, so no socket outlives the cut: the service connection, `ServiceClient`, the pool and the generator each dial through `cliffracer.core.dial.connect` (`test_a_cut_dial_leaves_no_descriptor_and_no_task_behind`).
- **Consequences**: Services fail startup predictably within the configured timeout rather than hanging indefinitely, unless a service sets `connect_timeout=None` and keeps the default reconnect budget, which restores the hang.

## ADR-0013: Mandatory Event Delivery Semantics
- **Status**: Accepted
- **Context**: In NATS, omitting queue groups or durable consumer names causes implicit broadcast across all replicas. Developers often forget this, inadvertently converting competing worker queues into duplicate fanout.
- **Decision**: Every `@listener` and `@validated_listener` must explicitly specify either `fanout=True` or `durable="<name>"`; `@broadcast` is an implicit fanout declaration. Omitting both raises `ConfigurationError` during handler discovery. `fanout=True` is a plain core-NATS subscription: every replica receives every message at most once, with no acknowledgement, redelivery or dead-lettering when the handler fails, even on a service with JetStream enabled. `durable="<name>"` is a JetStream queue consumer: one replica per message, acknowledged on success, redelivered on failure and dead-lettered at the delivery limit. A durable on a service with `jetstream_enabled=False` and without `fanout=True` is refused as inert; with `fanout=True` it is accepted and the durable does nothing until JetStream is enabled, at which point one subject declaring both is refused.
- **Consequences**: Prevents accidental replica event duplication in production by enforcing explicit operational intent at service definition time.

## ADR-0014: Non-Retryable Message Termination
- **Status**: Accepted
- **Context**: Retrying messages that failed deterministic schema validation or static authorization checks consumes broker resources, fills logs, and creates redelivery storms.
- **Decision**: Messages failing schema validation are by default routed to the Dead Letter Queue (DLQ) and terminated (`term()`). There is no unconfigured DLQ: `ServiceConfig.dlq_subject` defaults to `dlq.{service}`, and a JetStream service whose declared streams do not cover it fails at startup. What decides whether an invalid message is published is the handler's `on_invalid` on `@validated_listener` and, for every handler without one including typed `@listener` handlers, `ServiceConfig.default_on_invalid`: `"deadletter"` (the default) publishes it, `"drop"` logs it. A JetStream delivery is terminated in either case, and also when the DLQ publish itself fails, which is logged with the payload. That holds for a message dead-lettered at the delivery limit as well: the DLQ publish is best-effort on both paths. A failed publish is logged with its cause and the payload, counted in `dead_letters_lost` on `/health` (which leaves `status` alone), and the delivery is still terminated, because a redelivery would retry the publish only while the server has a delivery left and would loop a message that can never succeed. Static policy refusals (`RejectMessage`) acknowledge immediately; transient `RetryMessage` refusals NAK with a delay and dead-letter only at the delivery limit. What decides whether a JetStream delivery is retried is the phase and not the exception type: a failure before the handler is entered, while the payload is decoded, validated against its schema and built into the model the handler receives, is a judgement of the message and terminates the delivery whatever exception raised it, a model validator's `TypeError` as much as a `ValidationError` (the record's `errors` then holds one entry of type `validator_raised`), except a body in an encoding the service lacks the package to read, which is the service's fault and is NAKed like a handler failure, and a failure inside the handler is the handler failing and is NAKed for redelivery. A refusal carries no retryable flag: `RetryMessage` is the refusal that is retried, and `RejectMessage` is the one that is not.
- **Consequences**: Poison messages and unauthenticated requests are eliminated from the active stream immediately without redelivery loops.

## ADR-0015: Dispatch Context Isolation
- **Status**: Accepted
- **Context**: In asynchronous runtimes, task reuse and context variable inheritance can cause ambient trace or correlation IDs to leak between unrelated message dispatches.
- **Decision**: Every message dispatch initializes its own scoped `CorrelationContext` and resets the underlying `ContextVar` upon completion. Periodic timers reset the context before and after each execution.
- **Consequences**: Guarantees complete correlation isolation between dispatches; ambient IDs never leak across operations. A message that reaches several handlers is one unit of work: its id is resolved once, from the message or new, and every handler's dispatch carries it (`tests/unit/test_an_event_reaching_several_handlers_has_one_correlation_id.py`); each dispatch scopes it separately. Code outside the dispatch pipeline may read the ambient correlation id as a fallback when it is given no explicit one, and the outbound helpers and the dead-letter publisher do; an explicit id always wins.

## ADR-0016: Active Dependency Health Probing
- **Status**: Accepted
- **Context**: Passive boolean health flags fail to detect hung connections, network deadlocks, or unresponsive downstream dependencies.
- **Decision**: Declared dependencies execute an active round-trip probe with a bounded timeout during health checks, and so does the broker connection. A failed or timed-out probe returns HTTP 503. The core listener defaults to `127.0.0.1` to keep probe endpoints private by default.
- **Consequences**: Health status reflects real-time end-to-end operational viability rather than cached or stale startup flags.

## ADR-0017: Service and Container Separation
- **Status**: Accepted
- **Context**: Isolating NATS connection management, extension hooks, and message dispatch from application-level service logic improves maintainability and testability.
- **Decision**: `Container` manages broker connectivity, extension lifecycles, and dispatch pipelines. `CliffracerService` serves as the user-facing service interface, providing clean delegation to its internal container.
- **Consequences**: Clear separation of concerns between user-facing service definition and runtime message dispatch infrastructure. `svc.container` is exposed for tests and introspection; its API is not a stable public interface. The contract an extension relies on is the service's own `nc` and `js` properties, and the container reads only the surface of its service that the ADR-0017 note below names.

## ADR-0018: Extension Lifecycle and Combinatorial Testing
- **Status**: Accepted
- **Context**: The Cliffracer ecosystem consists of numerous opt-in extensions. Guaranteeing that any extension composes cleanly with any other in a $O(2^N)$ matrix is computationally impossible. Furthermore, probabilistic fuzzing in PR pipelines creates unacceptable flakiness, and shallow boot-testing fails to verify deep behavioral composition. 
- **Decision**: 
  1. **The Structural Composition Contract**: Extensions interact with dispatch only through documented hook points. Hook order is explicitly declaration-order dependent. Each extension strictly owns a namespaced config/env prefix, and port ownership is centrally arbitrated. The one exception is a variable that names a cross-cutting concern core also owns: it may live in the `CLIFFRACER_` namespace rather than the extension's own, and the log directory (`CLIFFRACER_LOG_DIR`, read by the logging extension) is the one such case. A check for the prefix rule names that exception.
  2. **The Composition Guarantee**: Cliffracer guarantees that *Supported* extensions comply with the composition contract. Compliance is enforced by construction where possible, and verified exhaustively in CI.
  3. **Testing Methodology**: 
     - **Deterministic Pairwise (PRs)**: The overwhelming majority of interaction bugs are pairwise. The CI pipeline executes an exhaustive, deterministic $O(N^2)$ pairwise matrix (e.g. `n-choose-2`) for all Supported extensions as a blocking gate. It also runs a single "all-enabled" megaservice smoke test.
     - **Nightly Higher-Order Fuzzing**: Randomized higher-order sampling (triples and up) runs in a nightly job. The seed is printed on failure for reproducibility (`--composition-seed=...`), and any discovered bug is promoted to a deterministic regression test.
  4. **Lifecycle Tiers** (declared in each package's `pyproject.toml` as `[tool.cliffracer] lifecycle`):
     - *Incubating*: Experimental, no composition guarantees, excluded from pairwise CI. The warning on import this tier is meant to carry is not built.
     - *Supported*: Stable, covered by the composition guarantee, actively tested in the pairwise matrix.
     - *Deprecated*: Supported but meant to warn on import (not built), slated for removal.

     A `[tool.*]` table is not shipped in a wheel's metadata, so the tier is readable from the source tree and by nothing in an installed environment. That is why no import warning is built: nothing installed can tell which tier it is in.
- **Consequences**: Provides strong, honest ecosystem stability guarantees without exponential CI bloat or probabilistic flakiness. Extension promotions to "Supported" require structural design review (e.g. how rate-limiting interacts with actor mailboxes), not just passing tests.
- **Implementation**: The testing machinery in clauses 3 and 4 is not built. There is no pairwise matrix and no all-enabled smoke test in CI, no nightly higher-order job and no `--composition-seed` option (no `conftest.py` adds pytest options), and nothing reads a lifecycle tier yet. Each package declares one in its own `pyproject.toml` (`[tool.cliffracer] lifecycle = "incubating" | "supported" | "deprecated"`), and `tests/repo/test_every_package_declares_its_lifecycle_tier.py` fails when a package has none or a value that is not one of the three. No import warning is emitted for *Incubating* or *Deprecated*, because nothing installed can read the tier, and the matrix is not built, so the declaration changes no behaviour today. The one scheduled workflow is the overnight chaos soak, which runs a single service under fault injection, not combinations of extensions. Until the machinery exists, composition is verified by each extension's own tests and the repository's structural guards.

The auth, OpenTelemetry and cyanide extensions hold no broker resource: searching `packages/*/src` for `subscribe`, `publish`, `key_value`, `add_stream` and `durable` finds nothing in them.

**Where two services can contend, and what stops them.** Streams are checked against the broker, so two services declaring the same stream name with different subjects cannot both start (measured: the second, in another namespace, was refused and the first stream left as it was). Nothing checks bucket names: two services that name the same bucket share it, which is how cron locks and the rate limiter are meant to work across replicas; both carry the subject prefix in the bucket name, and the cron lock keys carry the namespace, unescaped (a service named `a.b` with no namespace and a service named `b` in the namespace `a` share their keys, and only one of them runs a firing; escaping the dots would give every un-namespaced app new keys and run a firing twice on upgrade). Nothing compares two services' subjects or queue groups, so services that share a subject and a queue group share the work. There is no central registry of broker resources.

**Environment variables.** Core reads `CLIFFRACER_SUBJECT_PREFIX` (`ServiceConfig`, `ServiceClient` and the client generator) the client generator command reads `CLIFFRACER_NATS_URL`; the `cliffracer describe` and `cliffracer call` commands read `CLIFFRACER_NATS_URL`, `NATS_URL`, `NATS_CREDS`, `NATS_USER`, `NATS_PASSWORD` and `NATS_TOKEN` as the defaults of their connection flags; the `cliffracer run` command reads `LOGURU_LEVEL`, loguru's own variable, for the level of the stderr sink it installs when `--log-level` is not given; the cyanide extension reads `CLIFFRACER_CYANIDE_*`; the logging extension reads `CLIFFRACER_LOG_DIR`; the dead-letter inspector, the `dlq` command, reads `NATS_URL`, `NATS_CREDS`, `NATS_USER`, `NATS_PASSWORD` and `NATS_TOKEN` as the defaults of its connection flags; the other six packages read none (searching `src` and `packages/*/src` for `os.environ`, `getenv` and `env_prefix`). The "namespaced config/env prefix per extension" in clause 1 is therefore true of the variables that exist and is not enforced.

**The lifecycle tier is read from the source tree only.** Each package declares it as `[tool.cliffracer] lifecycle` in its own `pyproject.toml`, and `tests/repo/test_every_package_declares_its_lifecycle_tier.py` fails on a package with none or a value that is not one of the three. Nothing in `src/` or `packages/*/src` reads it, and a `[tool.*]` table is not part of a wheel's metadata, so an installed distribution cannot report its tier and clause 4's import warning has nothing to read. The pairwise matrix in clause 3 can derive its list from the tree. Which declaration an installed environment could read, and whether a central registry of broker resources is wanted, are open.

### What the code does today: ADR-0001 to ADR-0017

This section states what is true of the code; it decides nothing. A claim is held by the test named beside it, or says how it was measured. Where an ADR leaves a choice open, the section says what the code does now and stops there.

**ADR-0001.** The boundary is held by `tests/repo/test_persistence_boundary.py`, which reads core's declared dependencies, its imports and its public names against a list of database drivers and a class-name pattern. ## ADR-0019: Virtual Actor Model and State Fencing
- **Status**: Proposed
- **Package**: cliffracer-actors
- **Context**: The `cliffracer-actors` extension aims to introduce a Virtual Actor model using NATS primitives. While NATS subject-based routing and KV provide excellent building blocks, they do not magically solve distributed systems complexities. A naive implementation risks split-brain processing on network reconnects, silent message loss on fire-and-forget, and interest-graph memory leaks.
- **Decision**: The Actor extension is strictly an incubating feature governed by the following structural invariants:
  1. **Ask-only v1**: `tell` (fire-and-forget) is forbidden. Activation relies on the NATS `no-responders` error, which only exists for `ask` (Request-Reply). That status is delivered to the requesting client alone: no service ever sees it, and any subscriber whose subject matches the actor's removes it, so an activator subscribed to the actor subject space would answer every request and the error would never occur, and a silent wildcard subscriber (a monitor on `>`) turns it into a timeout. The client therefore catches `no-responders` and sends a second request on a distinct activation subject outside the actor subject space; a queue-grouped activator on that subject acquires the lock and instantiates the actor, and the client retries the first request, raising `ClientActorActivating` to its caller while activation is still in progress. The retry is bounded. Nothing but the actors themselves may subscribe to the actor subject space, and the broker must advertise headers, which the client's `no_responders` option follows.
  2. **Interest = Location. Lease = Right to Exist**: A NATS subscription routes traffic. Ownership is a KV document containing the holder and an absolute expiry timestamp, acquired with `create()` and renewed by a revision-checked update before that deadline. A contender may replace an expired document only with a CAS update against the revision it read; a concurrent renewal or takeover makes that update fail. Release also checks the held revision, so an old holder cannot delete its replacement. Expiry is evaluated by the reader and does not depend on per-key TTL support. The deployment must define and enforce a bound on wall-clock skew: holders stop before their deadline by that bound, contenders wait beyond it by that bound, and a node that cannot maintain the bound must refuse ownership. A failed renewal or an elapsed deadline fences local actors. A NATS disconnect fences them when it is noticed, which is not immediate: a restarted or reset broker connection is noticed in a fraction of a second (about 0.3 s, measured), but a silent partition only after `ping_interval` x (`max_outstanding_pings` + 1) seconds (measured as 3.0 s at 1 s and 2 outstanding pings, and 6.0 s at 2 s; 360 s by that formula for nats-py's defaults of 120 s and 2, which Cliffracer does not change). The lease deadline and the lease check before every side effect (item 3) are what keep a partitioned node from acting, not the disconnect callback. nats-py replays every subscription when it reconnects and has no per-subscription opt-out: left alone, an actor's subject received a message published after the reconnect (measured), and the only way to keep it out of the replay is to unsubscribe it before the reconnect completes (measured: unsubscribed inside the disconnect callback, the subject received nothing afterwards). Reconnect therefore does not restore ownership, and the extension removes its subscriptions itself; a fresh acquisition re-subscribes. The `Extension` interface has no disconnect or reconnect hook today; the one seam is the single `on_disconnect` slot of `ServiceConfig`. Bucket retention is separate from lease expiry and must not remove live ownership records or actor state. Per-key TTL on a capable broker is optional cleanup, not the ownership decision.
  3. **Fence Before Visibility**: A zombie actor is dangerous before it ever flushes state. No side effects (replies, outbound events, nested asks) may execute unless the actor currently holds a valid, unexpired lease. KV CAS on state flush is a secondary backup, not the primary fence. `write-behind` caching is forbidden in v1.
  4. **Working-Set Limits**: Actors require one exclusive NATS subscription each. To protect the NATS interest graph from exploding, the framework requires a hard per-process activation cap, idle deactivation (passivation), and strict unsubscription upon death.
  5. **Sequential Mailbox & Header Call-Chains**: Actor mailboxes process requests strictly sequentially via `asyncio` mutual exclusion. Reentrancy is disabled by default. Deadlocks are prevented structurally: every actor request appends its ID to a header call-chain, and any cyclical request (e.g., A -> B -> A) is immediately rejected with an `ActorCycle` error.
  6. **State is a KV Document**: Actor state is flushed as a document to NATS KV using leader-safe CAS. A read that must not be stale is served by the stream leader. A direct get is answered by whichever replica receives it, which can lag the leader on a replicated bucket, and a bucket's stream allows direct gets when `allow_direct` is set on it (`direct=True` in a declaration, or a bucket another client created with it). The actor's bucket is declared with `direct=False` (`BucketConfig` in the KV extension carries the setting), so its reads go to the leader. The lease holder reads once to hydrate and serves later reads from memory.
- **Consequences**: Safely bounds the scope of virtual actors to an explicitly leased, memory-capped, ask-only paradigm. Requires developers to design around cold-start activation latencies and strict single-threaded deadlock prevention.
- **Implementation**: None of the six invariants is implemented. There is no `cliffracer-actors` distribution, no `ClientActorActivating` or `ActorCycle` defined in `src/` or `packages/`, and no activator, lease, mailbox or passivation code for actors (the only lease in the tree is the cron extension's job lease). The invariants above are a design the ADR records, not behaviour the framework enforces, which is what Proposed means here.

## ADR-0020: A Taken Health Port Fails at Startup, and Port Zero Asks for a Free One
- **Status**: Accepted
- **Context**: Every service inherits the same default `health_port`. Two services in one process, or two processes on one host, therefore ask for the same port. Moving the second one to a port nobody chose keeps the process alive at the cost of a silent lie: the service is up, and the probe pointed at the configured port reads the first service's listener or nothing at all. Container healthchecks, orchestrator probes and operators all read that port by name.
- **Decision**: Binding the health port follows ADR-0010. A port already in use raises `OSError` at startup and the service fails to start. `health_port=0` is the explicit way to ask the operating system for a free port, the ordinary socket idiom; the port it assigns is reported on `/info` and in the line the listener logs as it binds.
- **Consequences**: Co-located services declare their ports, or ask for port zero and read back what they got. A probe aimed at a configured port reaches the service that owns it. Test and example processes that run several copies at once set `health_port=0`, which is why the examples runner sets it for every example that takes the default.

## ADR-0021: The Log Level Belongs to the Process
- **Status**: Accepted
- **Context**: Loguru's sinks are process-global. A level attached to a single service reads as a promise that each service in a process can log at its own level, and the orchestrator runs several services in one process, so the promise holds for whichever service configured the sink last.
- **Decision**: `cliffracer run --log-level` sets the level for the process. The orchestrator configures one sink before any service starts, and every service run by that command logs at that level. Leaving the flag off keeps the level loguru's default sink had (`LOGURU_LEVEL`, else DEBUG); the command still replaces that sink with one that prints a traceback's frames and not the values in them, as the sink the flag installs does, because the default prints a credential a failing frame holds. An application embedding these services through `ServiceOrchestrator` keeps the logging it set up itself: the command is what replaces the default sink.
- **Consequences**: The setting is described where it applies, on the command that owns the process, rather than on per-service configuration. An application that wants per-service filtering adds its own sink with a filter, which loguru supports directly and which the framework leaves to the caller. The one sink the framework adds per service, the NATS log stream, carries that filter: it publishes only the records bound to its service, so two streaming services in one process do not publish each other's lines, and a line with no `service` binding is not streamed.

## ADR-0022: Template Contracts and Explicit Service Activation
- **Status**: Accepted
- **Context**: Applications need separately addressable service instances whose creation, readiness and cleanup follow a bounded owner lifetime. A caller needs the RPC contract before an instance starts, and a retry must distinguish finding accepted work from creating another activation.
- **Decision**: A registered service template supplies its class, typed settings, revision, factory and fixed RPC contract. An optional local supervisor manages explicit activation under an owner, assigns a distinct address to each generation and binds ordinary generated clients to those addresses. It retains unfinished work, capacity reservations and generation checks until cleanup completes. Reactivation is explicit, and business-operation replay belongs to the application.
- **Consequences**: The [virtual-service contract](virtual-services.md) defines the local lifecycle, failure outcomes and retention bounds. The [local supervisor](local-supervisor.md) and [parent-owned shipment example](../examples/virtual_services/README.md) implement that contract. Application stores own durable state under ADR-0001. Persistent and remote placement remain proposed; distributed actor ownership and state fencing follow the additional contract in ADR-0019.

## ADR-0023: Core Depends on nats-py, pydantic and loguru
- **Status**: Accepted
- **Context**: Core is the one distribution every service installs. A dependency core declares reaches every service, including one that only exchanges messages. A dependency core imports without declaring works wherever a development environment has everything installed, and fails on a bare `pip install cliffracer`.
- **Decision**: Core's runtime dependencies are `nats-py`, `pydantic` and `loguru`, and no others. Anything else is an extension, its own distribution under `packages/` with its own dependencies, or an optional extra that core imports only behind a guard that treats an absent package as absent.
- **Consequences**: `pyproject.toml` declares the three (`tests/repo/test_dependency_lists_agree.py` holds the lists in step), and `tests/repo/test_core_import_closure_is_within_declared_deps.py` imports every core module in an environment that has every extra installed and refuses any installed distribution outside those three and what they pull in. A fourth core dependency is a decision recorded here, not an edit to a dependency list.
